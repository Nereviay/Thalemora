# 洄海维护与升级

本页对应 v0.6.0 的最小维护约定。版本来源是已安装包与固定发布提交；独立版发布不会自动升级宿主。

## 1. 版本与兼容范围

| 范围 | 已验证的约定 |
| --- | --- |
| 独立 v0.5.0 → v0.6.0 | 保留身份、来源、原话、Memory 修订和证据；首次维护会事务升级旧合成审计表并保留旧记录 |
| v0.6.0 的 backup / restore | 快照 format=1；停写后备份，恢复到新空目录，保留 Agent ID 并重绑定档案路径 |
| 念念宿主接入 | 已验证 dev2 公共核心与既有宿主的组合；公开 v0.6.0 不改变宿主已锁定版本、路径和数据 owner |
| 程序回退 | 只沿用 P6 已验的旧宿主程序读取最新数据范围；不据此保证独立实例任意整版降级兼容 |

升级说明必须列出配置/API/存储变化、迁移方向和可回退范围。没有对应说明和证据时，不把版本号相近当作兼容保证；不自动迁移 Prompt、改身份或交出写入权。

## 2. 平常检查什么

- HTTP 的 /health 是存活检查；Docker 已有 HEALTHCHECK。它不代表记忆质量或全部后台任务正常。
- 独立实例使用下列原有入口查看后台任务、候选、错误与 Provider 审计；管理台的“模型与用量”显示已知 Token、未知 usage 和预算状态。

```sh
thalemora --data ./state maintenance-status AGENT_ID APP_ID
```

- worker 遇到维护错误会记录原因并退出，不自动反复重试。修好配置或预算后再启动；不要为了检查而调用模型。
- 调用次数预算是累计上限；Token 预算按已报告消耗拦截下一次调用，最后一次可能越过阈值。actual_cost 未接供应商账单，不能把未知费用写成零元。
- 念念继续复用现有守护、定时健康检查和每分钟历史同步。检查只看服务、持久游标和任务回执，不扫原话、不调用模型，不放在每轮聊天前。

## 3. 备份与恢复

| 时机 | 最小动作 |
| --- | --- |
| 独立实例每周一次、每次升级前 | 先停止所有使用该数据目录的 HTTP/MCP/worker/脚本写入，再备份到新的目录 |
| 念念每日 | 沿用现有私有灾备任务；SQLite backup API 提供单库快照，在线逐库备份不是跨库同一时点恢复点 |
| 念念每次正式升级/切权前 | 在单独批准的维护窗口中冻结相关写入，使用已验宿主流程取得一致性恢复点；聊天与数据保护按当次方案执行 |
| 保留 | 原备份与 Git 历史保留，不自动清理；兼容验收结束前不删除上一恢复点。外部凭据、启动配置与可信宿主 reader 单独保管 |

独立实例执行：

```sh
# 先停全部写入；snapshot、restored 都用新的目录
thalemora backup ./state ./snapshot
thalemora restore ./snapshot ./restored
```

恢复后先核对 Agent/来源、原话、记忆修订、证据、内在记录和后台进度，再设置本地管理 token/模型环境变量，最后启动服务。恢复备份中的模型配置不等于必须立即启动 worker。

独立实例命令不能替代念念多库冻结流程。旧快照只恢复到隔离目录检查，不覆盖当前生产目录；重建派生索引也不能替代原始事实和正式修订。

## 4. 升级与出错处理

1. 记录当前包、宿主发布入口与配置。核对本次升级涉及的 API/存储变化，先做与影响范围相符的隔离验证。
2. 停相关写入并取得恢复点；独立实例换包，宿主按自己已批准的发布步骤换固定路径，避免双写。
3. 用最小请求检查真实写入/读取与后台进度。已有证据够用的部分沿用，不重跑全平台或付费模型矩阵。
4. 出错先停有问题的写入者并保存切后新增；普通聊天继续按宿主既有降级合同记录。查清原因后选择前向修复或已验证的程序回退。
5. 程序回退继续使用包含新增的最新数据。需要恢复正式数据或交还生产写入权时，先核一致性、影响与新增保全，再由部署拥有者明确批准；绝不直接用旧数据库覆盖新记忆。

v0.6.0 的一次停写恢复已用合成实例验证；宿主保留新增的程序回退沿用 P6 的既有演练。它们证明约定范围，不是无限版本、设备或长期稳定性保证。
